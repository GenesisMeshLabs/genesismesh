# Plan v0.63.0 — Pilot Readiness

## Context

The 2026-10-02 decision re-scoped the v1 gate (`ops/plan-v1.0.0.md`) for a
pilot. Two of its conditions are not yet evidenced: condition 1
needs a PostgreSQL backup restored to a new instance (and the v0.60 failover
test covers node certificate revocations, not the membership attestation
revocations a pilot depends on), and condition 3 needs a documented and
rehearsed pilot deployment profile. This release supplies both, so the next
step can be the 1.0.0 release rehearsal.

## Scope

### In scope

- A PostgreSQL recovery drill: a populated database is dumped with
  `pg_dump`, restored with `pg_restore` into a new database, and a new NA
  instance verifies every record and decision on it.
- HA failover with membership attestation revocations in flight: every
  acknowledged revocation persists exactly once and every later decision on a
  revoked attestation is denied.
- The pilot deployment profile (`docs/operations/pilot-deployment-profile.md`)
  and a rehearsal of it through the production entry point: two sovereigns,
  each a gunicorn NA configured only from the environment (environment key
  provider, PostgreSQL in HA mode for one of them, no proxy), operator keys
  generated by each operator, and the full recognition, attestation,
  revocation, feed import and rejection flow, plus backup, restore and
  readiness checks.
- CI for the drill and the rehearsal.

### Out of scope

- NA key rotation that keeps a sovereign's identity (security review SR-06):
  a protocol change to RFC-001 that needs its own design and RFC update.
- Naming the pilot's incident and 1.0.1 owner: the maintainer's decision.
- The 1.0.0 release rehearsal itself.

## Implementation

### Recovery drill

- `scripts/recovery_drill.py --postgres-url URL`: create a source database
  (C collation), populate it through the HTTP API (reusing the upgrade
  rehearsal's populate step), `pg_dump -Fc`, create a new database,
  `pg_restore`, start a new NA instance on it, run every verification of the
  upgrade rehearsal, and check `na verify-db`. `--pg-tool-prefix` runs the
  tools through another command (for example a `postgres:17` container) when
  the local client is older than the server.

### HA failover with attestation revocations

- `genesis_mesh/tests/integration/test_ha_failover.py`: a worker revokes
  pre-issued membership attestations through the load balancer while
  instance A is killed. Afterwards each acknowledged revocation is stored
  once, its attestation reads `revoked` on the surviving instance, and a
  decision on it is denied.

### Pilot deployment profile and rehearsal

- `docs/operations/pilot-deployment-profile.md`: the supported pilot shape,
  configuration, key custody, backup, upgrade, incident roles and limits.
- `scripts/pilot_rehearsal.py --postgres-url URL`: starts two sovereigns with
  gunicorn and `genesis_mesh.na_service.wsgi:app`, each configured only through
  environment variables, then:
  1. each operator generates its own keys; no key crosses sovereigns;
  2. sovereign A exports and validates B's trust bundle, takes B's key from
     B's live `/sovereign.json`, and issues a scoped treaty for B;
  3. B issues a membership attestation; A accepts it under the treaty;
  4. B revokes it; A imports B's signed feed and rejects the attestation;
     a replayed feed and a feed signed by the wrong key are refused;
  5. a standard-tier key cannot issue on either side;
  6. A's database is backed up, restored and verified (`na verify-db`), and
     both instances report ready.
- `.github/workflows/pilot-readiness.yml` runs the drill and the rehearsal on
  every change, with PostgreSQL 17.

## Security notes

Throwaway keys and temporary databases only. Seeds are passed to the NAs
through the environment, as a platform secret store would, and never written
to disk by the rehearsal. The rehearsal checks that keys never cross
sovereigns: each side receives only the other's public material.
