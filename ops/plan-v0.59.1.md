# v0.59.1 Plan -- TypeScript SDK for Governed Secret Lifecycles

## Context

Two pilots are planned on the v0.59.0 baseline: vendor service-principal
secrets requested through TechPartnerHub (Pilot 1), and one secret policy
across product teams and Azure subscriptions (Pilot 2). Both run a lifecycle
controller that asks the Network Authority for a signed decision, acts in the
cloud only on ALLOW, and submits signed execution evidence afterwards.

The core already provides everything the pilots need on the NA side: signed
attestations with claims (v0.58.1), declarative boundary policy with observe
mode and rollback (v0.58.0), attestation-backed evaluation, and the evidence
store with per-secret chains and export (v0.59.0). The pilot brief lists one
open client-side gap: the SDKs do not send `attestation_id`, cannot verify
attestation bindings, and do not wrap the evidence store. A TypeScript
controller would have to call the HTTP API by hand and re-implement the
Python canonical form to sign evidence.

v0.59.1 closes that gap in the TypeScript SDK, ahead of v0.60 (HA). It should
prove:

> A TypeScript controller can run the whole governed secret lifecycle --
> admit, decide, act, record, audit, offboard -- through the SDK alone, and
> every artifact it receives or produces verifies offline byte-for-byte
> against the Python reference.

## Versioning

The core leads the train (`docs/development/versioning.md`): an SDK change
between coordinated releases triggers the next coordinated patch. v0.59.1 is
therefore a coordinated release. The core bumps `VERSION` first; every other
component (Go, .NET, Rust SDKs, gateway) joins with a version-only change, as
for v0.59.0. Only the TypeScript SDK and the core docs change functionally.

## Scope

### In scope (TypeScript SDK)
- Python-parity canonical JSON, fixing two latent mismatches (below)
- Corrected `BoundaryDecision`, `MembershipAttestation` and related types to
  match the wire models (the 0.59.0 types predate v0.56 context decisions)
- Admin `GET` routes (signed empty body) and NDJSON responses in the transport
- Typed errors for 403, 409 and 503, carrying the NA `details` and
  `request_id`
- **Attestations:** get, list, verify, revocation feed, active recognition
  policy (issue, revoke and save-policy exist)
- **Boundary:** `evaluate` with an `agreement` or an `attestation_id` basis,
  returning the decision and justification proof
- **Boundary policy:** validate, publish, list, active, history, activate
  (also rollback), deactivate, verify
- **Evidence store:** submit execution evidence (idempotent duplicates
  reported), executor keys (register, list, retire), search with paging,
  resource and vendor history, store verification, status, export (paged
  NDJSON), retention
- **Execution recorder:** builds and signs `ExecutionEvidence` exactly as
  `record_execution` does, including the per-decision and per-resource chains
- **Offline verification:** decision signature, expiry and bindings
  (`expected_policies`, `expected_attestation`); attestation, policy,
  justification and checkpoint signatures; execution evidence signatures;
  full `gm.evidence.event` export verification (port of
  `verify_evidence_events`)
- **Metadata guard:** the NA's secret-material check, run client-side before
  anything leaves the controller
- **Governed action helper:** decide, act only on ALLOW, record the outcome
  (success or failure) on the resource chain, submit
- **Reconciliation helper:** latest recorded state per resource from the NA,
  compared with an observed cloud inventory (unmanaged, drifted, removed,
  revoked-but-present)
- **Pluggable signers:** operator and executor signing through an async
  `Signer`, so keys can live in an HSM or a cloud key service; the raw-seed
  signer stays the default
- **Opt-in retries** for idempotent requests (GETs, verification, evidence
  submission) on network errors, 429 and 503: groundwork for v0.60 failover
- Cross-language test vectors generated by the Python reference, checked in
  the SDK's unit tests
- A live end-to-end test against a locally started NA
  (`EVIDENCE_STORE=on`, `BOUNDARY_POLICY_ENFORCEMENT=required`)

### Out of scope
- Go, .NET and Rust SDK feature parity (version-only in this release)
- Cloud adapters (Graph, Key Vault, GCP), schedulers, TechPartnerHub
  integration: these belong to the pilot controller, not the SDK
- Recognition treaties and revocation-feed import (cross-sovereign; not needed
  by the pilots)
- Any NA, protocol or schema change

## Design

### 1. Canonical JSON parity

Every GM signature covers `json.dumps(..., sort_keys=True,
separators=(",", ":"))` of a Pydantic `model_dump(mode="json")`. Two
mismatches in `canonicalJson` would break signatures:

- **Non-ASCII text.** Python escapes every non-ASCII character
  (`ensure_ascii=True`): `é` becomes `é`, astral characters become
  surrogate pairs. `JSON.stringify` emits them raw. Today any admin request
  body with a non-ASCII value fails signature verification at the NA.
- **Numbers.** A JS number whose JSON text has a fraction or exponent is a
  Python float on the NA, re-serialised with `repr`: `1e-05`, `1e+21`,
  `1.5e+16`. The canonical form now emits that text.

Timestamps the SDK creates use Pydantic's form: microseconds, `Z` suffix,
fraction omitted when zero (`2026-10-01T08:10:01.561000Z`). JavaScript's
`toISOString()` form (`.561Z`) would be re-serialised differently by the NA
and the evidence signature would fail.

One limitation stays and is documented: an integral Python float (`1.0`)
parses to the JS number `1`, so a record carrying one cannot be re-verified
offline in JS. GM models do not use floats; controllers should keep evidence
metadata to strings and integers.

### 2. Verification parity

Offline verifiers are direct ports of the Python functions, with the same
reason codes, so a TypeScript auditor and the NA agree:

- `verifyBoundaryDecision` -- `trust/context/decisions.py`
- `verifyEvidenceEvents`, `parseExportLines` -- `trust/evidence_store.py`
- `attestationDigest`, `policyDigest`, `policySetDigest`,
  `executionDigest` -- the model `digest()` methods

Canonical bodies are derived from the received JSON by removing the field the
model excludes (`signature` or `signatures`) and the optional fields Python
omits when absent (`policy_binding`, `attestation_binding`, the v0.59
resource-chain fields).

### 3. Layers

`auth.ts` holds every key operation: canonical JSON, digests, signing,
verification, the `Signer` interface. New pure modules hold the protocol
logic: `execution.ts` (recorder, metadata guard), `verify.ts` (offline
verification). Sub-clients stay thin wrappers over the transport. `governance.ts`
composes sub-clients for the controller flow and reconciliation.

### 4. Controller flow

```ts
const gm = new GenesisMeshClient({ baseUrl, signer: operatorSigner });
const recorder = new ExecutionRecorder({ executorSovereignId: 'secrets-controller', signer: executorSigner });

const result = await governedAction(gm, recorder, {
  attestation_id, requested_capability: 'sp-secret.rotate',
  context: { request_parameters: { app_id, lifetime_days: 90 }, attributes: { owner, secret_store: 'azure-key-vault' } },
  resource_id: `kv:${vault}/${secret}`, resource_action: 'rotate',
}, async () => ({ execution_parameters: { secret_version: await rotateInKeyVault() } }));
```

`governedAction` never calls the action on a DENY. It reads the resource head
from the NA (or uses one supplied by the caller), records a failure outcome
when the action throws (then rethrows), and treats a duplicate submission as
success.

## Security notes

- The SDK never sees secret values unless the caller passes them; the guard
  rejects obvious secret material before signing, mirroring the NA.
- Signing errors propagate; no fallback key formats; no key caching.
- Retries are opt-in, bounded, and limited to idempotent requests. Admin POSTs
  that create state (attestation issue, policy publish) are never retried.
- Offline verification fails closed: unknown executor key, missing
  signature, or a payload that does not parse gives a failure, not a skip.

## Tests

- Unit tests per public method: happy path, URL, admin headers, typed error.
- Canonical JSON: unicode, astral characters, floats, nested ordering.
- Python-generated vectors: a decision with attestation and policy bindings,
  its justification proof, an attestation, a policy, execution evidence on a
  resource chain, a retention checkpoint, and a full NDJSON export. The SDK
  must reproduce every digest and verify every signature, and must detect a
  tampered copy of each.
- Recorder: TS-signed evidence accepted by Python `verify_model_signature`
  (vector round trip).
- Live E2E (local NA, opt-in via `GM_E2E_BASE_URL`): issue a vendor
  attestation, publish and activate a policy, register an executor key,
  create / rotate / revoke a secret through `governedAction`, get a signed
  DENY for an app outside the claims, revoke the vendor, confirm the next
  decision is denied and evidence is refused, then verify the vendor and
  secret history and the export offline.

## Success Criteria

- A TypeScript controller runs Pilot 1 end to end against a local NA with no
  hand-written HTTP or crypto.
- Every artifact the NA signs verifies offline in TypeScript, and every
  TS-signed evidence record is accepted by the NA.
- Non-ASCII admin request bodies verify at the NA.
- No runtime dependencies are added.

## Release Gate

1. Core: `VERSION` 0.59.1, changelog, docs; CI and release train green.
2. TypeScript SDK: build, typecheck, unit tests, live E2E against a local
   NA at core `main`.
3. Go, .NET, Rust SDKs and gateway: version-only bump, CI green.
4. Tags `v0.59.1` signed in every repository; registries publish; the Azure
   VM deploy of the core tag is green.

## Decisions

1. **Coordinated patch, not an SDK-only number.** Required by the train.
2. **Type corrections ship in a patch.** The old `BoundaryDecision` type never
   matched the wire, so correcting it fixes callers rather than breaking them.
3. **Async signer, seed by default.** Prepares non-exportable signing without
   changing existing constructors.
4. **Reconciliation is a comparison, not a scanner.** The SDK compares an
   inventory the controller supplies with the NA history; discovering cloud
   state stays in the cloud adapters.
