# Plan v1.11.0: the new release model

Decision [0001](../docs/development/decisions/0001-release-model.md) (accepted 2026-10-16) replaces the lockstep train with:
- independent component patches;
- no empty releases;
- a pinned contract bundle;
- a tested compatibility table.

`ops/plan-contract-bundle.md` is its detailed implementation contract. This plan rebases that design onto 1.10.1 and adds what the 1.10.x releases taught. Where this plan says nothing, the bundle design stands.

This is a release-process workstream. It runs alongside the 1.11 functional scope (`ops/plan-v1.10.0-adoption.md` items 3 and 2) and does not take in the rest of Phase C.

## 1. Why now

1.10.0 and 1.10.1 showed what lockstep costs:
- **1.10.1 changed only the gateway image** (gateway #93). Five repositories released "nothing changes" versions, each with its own CI runs and registry entries.
- **The core 1.10.0 image failed to publish** because the harness built the gateway from `main` and compared its label with the core's version. The core image had to wait for a gateway version bump.
- **The core merge queue failed twice on Interoperability** (core #150). It compares the vectors with each SDK's `main`, so the SDKs had to merge first.
- **A gateway security fix** (the zlib CVEs) could not ship without a release of every repository.

## 2. Target model

1. **Independent patches.**
   - A component releases when its code, its dependencies or its distributed artifacts changed.
   - No unchanged SDK or gateway is published to match another component's number.
2. **The core leads major.minor** (decision 0001).
   - A component's `major.minor` may not exceed the `major.minor` of the released bundle it pins.
   - A component may stay on an older minor when it is compatible.
   - A matching number is never taken as proof of compatibility: the compatibility table is.
3. **Strict signed-field parsing stays.**
   - When a contract change makes older verifiers refuse new records (1.10.0's signed requester gives `unknown_field` in 1.9.x), the affected SDKs release before, or together with, the Network Authority that emits the new field.
   - The compatibility table records that pair as not compatible.
4. **A release manifest names each recommended set.** It lists exact component versions, the contract bundle, artifact digests and the test evidence. Users keep a known-good set without matching numbers.
5. **Immutable tags stay immutable.** A failed release is fixed by the next version, never by moving or replacing a tag.

## 4. Decisions this plan takes

1. `bundle_version` equals the core version that publishes it. A `contract_digest` shows when two bundles carry the same contract (bundle design, decision 1).
2. **No bot** (Maintainer, 2026-10-16, binding). Pin-bump and consumer-pin workflows open or update an issue with the exact `gm_contract.py sync` command. The coordinator opens the bump PRs.
3. **Core Interop runs against pinned consumer releases** (`contract/consumer-pins.json`), never against SDK `main`. Canaries cover consumer `main` × core `main` nightly and are never required checks.
4. **The release manifest is generated by `devtools/release.py`.** It resolves every artifact version and digest once; those exact artifacts are tested; only then is the manifest published.
5. **Image checks are not weakened to major.minor.** Every image must:
   - match its own binary (`--version`);
   - match the manifest entry (version, digest);
   - pass its signature verification (cosign identity of its own tag's workflow) and the Trivy gate.

## 5. Work packages

One tested PR at a time, against `main`, no stacked PRs. Core PRs run the PostgreSQL suite before push.

### 5.1 Core: the contract bundle (bundle design C1 and C2)
- `scripts/gm_contract.py` (stdlib only) and `contract/bundle.json` (#155), with tiers:
  - `verifier`: sdk-go;
  - `governed`: sdk-typescript, sdk-rust, sdk-dotnet;
  - `edge`: sdk-rust edge;
  - `gateway`: gateway;
  - plus a tier entry for `vouching`.
- `genesis_mesh/trust/kinds.py` and generated `contract/kinds.json`; generated `contract/MANIFEST.json`.
- The required CI job "Contract bundle":
  - the manifest is current;
  - every suite has a tier;
  - the archive builds identically twice.
- `contract-bundle.yml` attaches `genesis-mesh-contract-X.Y.Z.tar` (uncompressed: deflate output differs between platforms, and the checksum must not), `SHA256SUMS-contract` and their sigstore bundles to the core release. It never creates the release.
- **Unknown-field coverage.** The bundle must carry, as required kinds for every tier, the vectors where a record with an unknown signed field is refused (`field_registry` `unknown_fields`). Rejected cases count as much as accepted ones.

### 5.2 Consumers: conformance receipts (bundle design X1)
One PR per repository (sdk-typescript, sdk-go, sdk-dotnet, sdk-rust, gateway). Every vector runner writes a receipt when `GM_CONFORMANCE_RECEIPTS` is set. No dependency: this can start immediately.

### 5.3 Core: stop reading consumer branches (bundle design C3)
- `contract/consumer-pins.json`, initially at each consumer's 1.10.1 tag. Interop checks out those tags.
- `ci.yml` container job and `publish-image.yml`:
  - the gateway comes from the pinned release, by digest, not from `main` or a tag of the core's version;
  - `container_smoke.py --gateway-version` checks label = manifest version = binary.
- `check_release_train.py` keeps only the core's own monotonic check. The cross-component ceiling moves to the nightly audit.

### 5.4 Consumers: pin the bundle and replace the train checks (bundle design X2)
One PR per repository, after the core 1.11.0 bundle exists. Before that, use a commit pin and do not release.
- `contract-bundle/{consumer.json,bundle.lock,MANIFEST.json}`, the vendored tool, and the required job "Contract bundle" (`verify --online`, `conformance`).
- The `release-train` job (same name, still required) runs `gm_contract.py release-check`:
  - the pin is coherent;
  - the ceiling holds;
  - on a release, the pin is a released bundle and something changed since the previous tag.

  The core-tag `ls-remote` checks and the curls of core `main`'s `VERSION` are removed.
- Every "Choose the core revision" step reads the pinned core commit.
- `canary.yml` runs nightly against core `main` and opens an issue on failure; it is never required.
- `contract-pin.yml` is issue-only (decision 4.2).

### 5.5 sdk-rust: verifier and edge tag streams (bundle design X3)
- `genesis-mesh-verify-vX.Y.Z` and `genesis-mesh-edge-vX.Y.Z`, each with its own release and changelog root.
- **Maintainer:** add both patterns to the "release tags are immutable" ruleset before the first stream tag.
- Until a stream's first release, the manifest records the verifier and edge at their last `v1.10.x` assets.

### 5.6 Release tooling (devtools and the shared config)
- **`release.py`:**
  - **Component selection.** `prepare` and `tag` act on the named components only. Without names, they act on the components with changes since their last tag (`git diff` over the stream paths), never on all six.
  - **Explicit steps.** `prepare` (release PRs), `tag` (signed tags, nothing else) and `publish-core-release` are separate commands. `tag` no longer creates the core GitHub release; that happens only when the core is among the components.
  - `manifest VERSION-SET` resolves every selected artifact once and writes the release manifest (§5.7): PyPI file hashes, npm `dist.integrity`, the NuGet package hash, the Go proxy `.info` and module hash, GitHub release asset hashes, and image index digests.
  - `status` reports per component, not per train version.
- **`check_version`:** checks a component against its own version files and its pinned bundle, not against the other repositories.
- **The Renovate preset:** a consumer (sandbox, genesismesh-mcp, genesismesh-web) gets one PR per component release. The grouped "Genesis Mesh train" rule that assumes one version is removed. Exact pins stay where they are today (genesismesh-mcp pins `genesis-mesh==X.Y.Z`).

### 5.7 The release manifest and the compatibility table
- **Release manifest** (`gm.release-manifest/1`). It records:
  - the set name and date;
  - per component: version, tag, commit, the bundle it pins, and every artifact with its digest:
    - wheel and sdist sha256;
    - npm integrity;
    - nupkg sha512;
    - Go module `h1:` hash;
    - GitHub assets sha256;
    - image index digests per image;
  - the cosign identity expected for each signed artifact;
  - the evidence: the published-artifacts run URL and its result, and the compatibility table revision.
- **`published-artifacts.yml` takes a manifest, not a version.**
  - It downloads every artifact by the recorded version and checks the recorded digest.
  - It verifies signatures with each component's own tag identity.
  - It runs the scenario.

  A manifest is published only after that run passes. A failed run leaves no manifest, and the previous set stays the recommended one.
- **Compatibility table** (bundle design C4), nightly and on every bundle release. Rows are each component's latest releases (current and previous minor); columns are the latest bundles.
  - A cell is `pass`, `fail`, `n/a (pre-bundle)` or **`refuses newer records`**: the expected result when an older verifier meets a newer signed field. That last state is never shown as compatible.
  - An untested combination is blank, never "compatible".
- **Where the manifest lives:** open decision 1 (§9).

### 5.8 Documentation and process
- `docs/development/versioning.md` rewritten (bundle design C3); ADR 0001's "Implemented" line updated.
- `.agents/skills/ship/SKILL.md` and `.agents/skills/sdk-ship/SKILL.md`, and `ops/release-checklist.md`: the per-component flow and the manifest step. AGENTS.md requires `/ship` for every release, so the skills must match the gates before cutover.
- The Releasing sections of every consumer (CONTRIBUTING.md / AGENT.md; sdk-rust `RELEASING.md` per stream; gateway `docs/distribution.md`: "a CVE patch ships as X.Y.Z+1 without a core release").

## 6. Safeguards
- Images are checked against their own binary and the exact manifest entry, with signature and Trivy gates intact. None of them compares only major.minor.
- Artifact versions are resolved once; the published-artifacts run tests exactly those; the manifest is published last.
- No tag is moved or replaced. A broken release is superseded by the next patch of that component.
- Strict signed-field parsing is unchanged. The bundle's rejected vectors are required checks.
- The current lockstep path stays usable until the rehearsal (§7) passes. Old and new checks run side by side during the transition. A new check only becomes required after it has been green on `main`.

## 7. Rehearsal before cutover
Run on the post-1.10.1 `main` of every repository, without publishing a real release:
1. **A component-only patch.**
   - A gateway patch prepared with `release.py prepare --component gateway`.
   - `distribution.yml` run as a dry run (`workflow_dispatch`; it publishes nothing).
   - `release-check --release` passes.
   - The manifest is generated with the other components at 1.10.1.
   - published-artifacts runs on that manifest with the gateway candidate image by digest.
2. **A contract-breaking minor.**
   - On a core branch, add a signed field to one record kind and regenerate the bundle.
   - Expected results:
     - the bundle check names the newly required kind per tier;
     - consumer canaries go red with an issue;
     - pinned consumers stay green;
     - the compatibility table shows `refuses newer records` for the old SDK pins.
3. **A failed publish.** Make one artifact of a dry-run manifest wrong (a digest or a missing asset). The published-artifacts run must fail, and no manifest may be written.
4. **The real 1.10.1 set as a baseline.** Generate the 1.10.1 manifest from the published registries and images. Verify it end to end with the new published-artifacts. The 1.10.1 artifacts passed the current published-artifacts workflow on 2026-11-10 (run 42919991842, every job green).

If any rehearsal fails, fix the gate and repeat. Nothing is released on a failed rehearsal.

## 8. Cutover at 1.11.0
1. Core 1.11.0 is released with its functional scope and the first contract bundle.
2. Each consumer that has something to ship pins bundle 1.11.0 and releases; one that changed nothing stays on its version.
   - When 1.11.0 changes a signed record, the affected SDKs release first or together with the core, as 1.10.0 required.
   - The gateway follows the same rule.
3. `release.py manifest` writes "Genesis Mesh 1.11.0" with the exact set, published-artifacts verifies it, and the manifest is published.
4. `versioning.md`, the ship skills and the checklist switch to the new model in the same release.
5. From then on, a patch is released only for the component that changed, followed by a new manifest for the set.

## 9. Open decisions for the Maintainer
1. **Where the release manifest lives and who signs it.**
   - *Recommendation:* a committed `releases/<set>.json` in the core repository, added by a reviewed PR, plus a signed copy (cosign `sign-blob`, identity of a core workflow on `main`) attached to a GitHub release named after the set.
   - The core release stays the natural anchor for a minor.
   - A component-only patch adds a set such as `1.11.0+gateway.1.11.1`. Alternatively, sets get their own names (`2026.11.1`).
2. **The Rust verifier and edge tag streams in 1.11 or later.**
   - *Recommendation:* in 1.11, since the manifest names them.
   - The ruleset edit is yours.
3. **The Network Authority reports its contract bundle version** (`/health` `contract_bundle`) so an older SDK can name the mismatch instead of only `unknown_field`.
   - *Recommendation:* yes, small and additive.
   - Parsing stays strict.
4. **The required-check changes on each repository** (add "Contract bundle", keep `release-train` with its new meaning, remove the core-main dependent checks). These are ruleset edits.
   - *Recommendation:* make them in one batch per repository, right after its X2 PR merges.

## 10. Done when
- Every consumer's required checks read only its own repository, its pinned core commit and immutable release assets.
- Over the 1.11 cycle, CI failures caused by another repository are 0.
- A patch of one component releases that component and a new manifest, and nothing else.
- The compatibility table and the "Genesis Mesh 1.11.0" manifest are published and pass published-artifacts.
