# Plan v1.1.0 — Signed Container Images

1.1.0 also ships the local governed Network Authority and the new admin
rate limits of `plan-v1.1.0-local-governed-na.md` (Decisions, 12).

## Context

Since v1.0.0 a Network Authority is installed with `pip install genesis-mesh`,
and the trust gateway from its signed release binaries or the OCI archive
(`gateway-oci.tar`) attached to its GitHub release. Neither is available from
a container registry. Operators who run containers build their own Network
Authority image from the repository-root `Dockerfile`, which copies the whole
source tree into `/app` and runs as a system user, or load the gateway archive
by hand. They cannot pull a released version by name, and nothing ties a
running image to a release.

This release publishes both components as signed multi-platform images, built
from the release tag, with a container contract operators can depend on. The
images are a new stable surface, which makes this a minor release.

Testing the images as two independently operated sovereigns, before anything
was published, found fixes and operator features the images need. They shipped
first, in 1.0.2 (section 7); this release builds on them.

## Scope

### In scope

- **Network Authority image** (`genesismesh`):
  `ghcr.io/genesismeshlabs/genesis-mesh`, the Network Authority or a mesh
  node (`SERVICE_ROLE`), built from the tagged source.
- **Gateway image** (`gateway`): `ghcr.io/genesismeshlabs/genesis-mesh-gateway`,
  the gateway and `genesis-mesh-operator`. The `gateway-oci.tar` release asset
  stays and holds the same image.
- `linux/amd64` and `linux/arm64`, SBOM and provenance, keyless Sigstore
  signatures that the publishing workflow verifies before tagging.
- The container contract: NA image **stable**, gateway image **beta**, in
  `contract/public-surface.json` and `DEPRECATION_POLICY.md`.
- A vulnerability gate, a container smoke harness run in CI, before publishing
  and against the published images.
- `start.sh` for the image: secrets passed in the environment moved to a
  private in-memory directory, a group-writable `/data`, and the node's invite
  token handed over with `--invite-token-file` (1.0.2).
- Removing `NA_ADMIN_LEGACY_SIGNATURES` (1.0.2's client migration setting):
  a Network Authority accepts only version 2 admin signatures.
- Documentation, including a new Container Images page and upgrade notes.

### Out of scope

- Registries other than GHCR (see *Registry choice*).
- Helm charts and Kubernetes operators. The Kubernetes example is fixed and
  moves to the published image; nothing more.
- Images for the SDKs. They are libraries and stay on their language
  registries.
- `sdk-php`: not on the release train.
- Running deployments: the reference Network Authority, the Azure VM, the
  live mesh demo (`infrastructure/mesh-demo`) and the apex site. They may move
  to the published images after the release; that is operations work, not
  part of this release.
- `infrastructure/pilot-vm` keeps installing the released PyPI package: it
  rehearses the PyPI path, which this release does not replace.

## Registry choice

GHCR is the registry of record:

- It lives in the same organization as the source. A workflow pushes with
  `GITHUB_TOKEN`, so there is no new long-lived secret.
- Each package links to its repository, and cosign signatures are stored next
  to the image.

Docker Hub would improve discoverability. It would also add an account, a push
token, and anonymous pull limits for operators. A Docker Hub mirror of the same
signed digests can follow later without changing the container contract.

## Design

### 1. Network Authority image (`genesismesh/Dockerfile`)

- **Build stage** (`--platform=$BUILDPLATFORM`): `python -m build --wheel
  --no-isolation` with build tools pinned by hash (`requirements-build.lock`).
- **Runtime stage**: `python:3.14-alpine` pinned by digest. Installs the
  dependencies from `requirements-image.lock` (hashes required, generated by
  `scripts/lock_image_requirements.py`, checked by `test_image_lock.py`), then
  the wheel with `--no-deps`. Alpine security updates are applied at build
  time. `pip` and the bundled `ensurepip` wheels are removed.
- Runs as user 10001. `/data` is the working directory and state directory,
  owned by 10001 and group 0, mode 2770, so platforms that assign an arbitrary
  user ID in group 0 work too. `DB_PATH` defaults to
  `/data/genesis_mesh_na.db`. No `VOLUME`: with a read-only root file system
  and no mount, the NA refuses to start instead of writing to an anonymous
  volume.
- `tini` is PID 1 and runs `start.sh`. `HEALTHCHECK` calls `/readyz` for the
  NA role. OCI labels carry version, revision, source, documentation and
  licence; the Dockerfile syntax image is pinned by digest.
- `start.sh` writes secrets passed in the environment (`GENESIS_JSON`,
  `NA_PRIVATE_KEY`, the seed) to a private directory on `/dev/shm`, removes
  them from the environment before `exec`, refuses to start on a SQLite
  database it cannot write (including `DATABASE_URL=sqlite:///…`), and
  validates `NA_KEY_SEED_ENV`.
- `.dockerignore` is an allowlist (package, `start.sh`, locks, healthcheck),
  with keys, `.env` files and databases excluded at every depth. The harness
  plants such files in a copy of the build context and checks that none
  reaches the image.

### 2. Gateway image (`gateway/Dockerfile`)

The existing distroless build, with the Rust build image and the syntax image
pinned by digest, OCI labels from `VERSION`/`REVISION` build arguments, and
`WORKDIR /var/lib/gateway` (the distroless home belongs to another user). The
repository gains the MIT `LICENSE` file its manifest and labels already
declare.

### 3. Container contract

`contract/public-surface.json` lists both images under `packages`: the NA
image stable, the gateway image beta like the gateway. `DEPRECATION_POLICY.md`
gains a *Container images* section: `X.Y.Z` is never moved; `X.Y` and `latest`
follow the newest release; the signature is part of a release; the image
name, `SERVICE_ROLE` values, documented variables, `/data`, port 8443, user
10001, the health check and failing closed are stable; base image and OS
packages are not.

### 4. Publishing and immutability

**Network Authority** (`.github/workflows/publish-image.yml`), on
`release: published`, the event `publish-pypi.yml` uses:

1. `check_version.py --tag` and `check_release_train.py` (with
   `RELEASE_TRAIN_TOKEN`). One concurrency group per release tag.
2. Ask the registry whether `X.Y.Z` exists. Only an answer of "not found"
   counts as absent; any other error stops the run.
3. Build `linux/amd64` and load it; run the vulnerability gate and the full
   harness on it (every scenario, with the gateway of the same release or
   `main`, an image built from the 1.0 Dockerfile and the Compose file).
4. Build both platforms and push **by digest only** (no tag yet), with SBOM
   and provenance, and check that the pushed `linux/amd64` image has the same
   layers as the image that was scanned and tested.
5. On an arm64 runner, pull the pushed arm64 variant and run the
   vulnerability gate and the Network Authority scenarios on it natively.
6. `cosign sign --recursive` the digest, then `cosign verify` it with the
   workflow identity at the tag.
7. Tag `X.Y.Z`, plus `X.Y` and `latest` only when this is the newest release
   (`scripts/image_tags.py`; GitHub's pre-release flag does not change this,
   as it does not for PyPI). A tag already on the digest is left alone;
   `X.Y.Z` on another digest stops the run.
8. Append the digest to the GitHub release notes unless they list it.

A `workflow_dispatch` run is a dry run: it builds, scans and tests both
architectures (arm64 built on the arm64 runner) and asks the registry whether
the version exists (so the first release does not meet that check new), and
never pushes or signs.
When `X.Y.Z` already exists (the release event fired again, or the run is
re-run after tagging), the run skips the build, verifies the published
digest's signature and completes steps 7 and 8, so a re-run after a late
failure finishes the release instead of failing. A failure before tagging
leaves only an untagged, unsigned digest; the re-run builds again. Never
recover with a dispatch run, whose signature would carry a branch identity.

**Gateway** (`distribution.yml`) on a tag push, after `cargo test` passed on
both platforms: the same steps, with its own gate (no high or critical
finding, no secret) and the gateway scenarios against the Network Authority
built from the core tag of the same release. One build has two outputs, the
OCI archive and the push by digest, and the archive's index digest must equal
the pushed digest. The archive is signed (`sign-blob`) and attached to the
GitHub release, whose notes get the image digest. When `X.Y.Z` already
exists, the published image is exported with its digests (`skopeo`) for the
release archive. Job permissions are declared in full; a dispatch run, even
on a tag, never pushes, signs or releases.

**Release order.** The core leads: tag and publish the core release first,
then tag the gateway. The gateway's image job builds the Network Authority
from the core tag of the same version and fails at checkout without it.

### 5. Vulnerability gate

`scripts/image_vuln_gate.py` reads a Trivy report (Trivy pinned by digest)
and fails on any critical or high finding, in an OS package or a Python
package, with or without a released fix, on any secret, and on a report that
lists no OS packages. The Network Authority image is built on Alpine, whose
packages carry no such findings (on Debian 13 slim there were 44 high
findings, 8 distinct CVEs without a fix, in packages the image never uses).
The gateway keeps the same rule, which its distroless image passes.

### 6. Tests

`scripts/container_smoke.py` starts real containers on a private network and
removes everything it creates. Key custody follows the roles: `init` output
stays in a volume only the harness reads; the NA gets its genesis and key,
the operator CLI its configuration and operator key, others only public
material; no container gets a root key or another sovereign's keys.
Scenarios:

| Scenario | Checks |
| --- | --- |
| `na-metadata`, `na-contents`, `na-version` | user, entry point, labels, no source tree or `pip`, version of the package and of `genesis-mesh --version` |
| `na-fail-closed` | ten refusals: no genesis or key, `env` provider without a seed, malformed `NA_KEY_SEED_ENV`, another sovereign's key, read-only root without `/data`, unwritable `sqlite:///` path, missing database directory, unknown role, node without genesis, node without invite |
| `na-file-provider`, `na-env-provider`, `na-secret-file` | the file and environment key providers (Key Vault is covered by unit tests); the seed absent from the server processes' environment and from the writable layer |
| `na-hardened`, `na-writable-layer`, `na-arbitrary-uid`, `na-healthcheck` | read-only root and dropped capabilities, secrets passed in the environment never written to the writable layer, user 12345 in group 0, health check states |
| `na-persistence-node`, `stop-graceful` | state across restarts, a node enrolled with an invite, clean stop on `SIGTERM` |
| `na-ha-refuses-file-key`, `na-postgres-ha` | HA refuses key files; two instances on PostgreSQL share invites |
| `gw-metadata`, `gw-end-to-end`, `gw-crl-refresh` | gateway contract, policy from the operator tool, state initialised once, a revocation reaching the gateway by CRL refresh |
| `fed-two-sovereigns` | two sovereigns with their own keys exchange bundles and treaties, then cross-sovereign attestation, revocation and feed import with each operator acting alone; a forged treaty refused; a client of one sovereign refused by the other |
| `na-upgrade-from-legacy`, `build-context`, `compose-example` | volume handover from a 1.0 image, build-context exclusions, the Compose file with both images |

It runs on every change in both repositories, natively on amd64 and arm64
runners: the core's `container` job builds the gateway from the branch of the
same name when it exists (else `main`), and the gateway's builds the Network
Authority from the core branch of the same name (else `main`, skipping the
harness until `main` has it). The release workflows run it before tagging
(section 4), and `published-artifacts.yml` runs it against the published
images on both architectures (anonymous pull, signatures with the exact
identities, floating tags on the released digest), skipping versions before
1.1.0.

### 7. Built on 1.0.2

Running the two-sovereign scenario before publishing found what 1.0.2 then
shipped: admin signature version 2 (method, path, query and the target NA's
public key), treaty and feed checks against pinned keys only, signing only in
the NA's own name, agent routes for keys containing `//`, and the operator
features the images use (`NA_PRIVATE_KEY_SEED_FILE`, `genesis-mesh
--version`, the one-sovereign-at-a-time CLI commands, a `/readyz` that proves
the database is writable, a node that stops on `SIGTERM` and reads its invite
token from a file). The images rely on them and change none of them.

### 8. Upgrade and migration

- No database migration: rolling back to 1.0.2 on the same database works.
- From 1.0.0 or 1.0.1, follow *Upgrading to 1.0.2* first: admin clients and
  Network Authorities must agree on the signature version.
- Images built from the 1.0 Dockerfile ran as uid 100 in `/app`. A volume
  they wrote is handed to uid 10001 once; the new image refuses to start until
  then and says how.

## Security notes

- Images never contain key material. Keys reach the container by mounted file,
  secret file (`NA_PRIVATE_KEY_SEED_FILE`), environment or Key Vault; the docs
  say that environment values are visible to anyone who can inspect the
  container.
- Signatures are keyless and bound to the release workflow at the release
  tag. Operators verify that exact identity; any other signature is not a
  release.
- Published `X.Y.Z` tags are never moved. Floating tags only move forward.
- Both GHCR packages start **private**; making them public is a Maintainer
  step in the Release Gate and cannot be undone.

## Decisions

1. **Two images**, one per repository: the Python Network Authority and the
   Rust gateway are separate products with separate release workflows.
2. **GHCR**, with a Docker Hub mirror possible later (see above).
3. **NA image stable, gateway image beta**, matching the components.
4. **Keyless signatures, push by digest, tag last.** An existing `X.Y.Z`
   stops the workflow.
5. **Vulnerability gate**: any critical or high finding blocks, fixed or not,
   for both images (section 5). The NA image moves to Alpine to meet it.
6. **`genesis-mesh --version`** (1.0.2) is what the image's version check
   uses, rather than `__version__` only.
7. **A health check in the NA image**, on `/readyz`.
8. **The gateway repository gets its MIT `LICENSE`** in this release.

9. **Version 1.1.0** (Maintainer, 2026-10-05): the images are a new stable
   surface, the image is not a drop-in replacement for one built from the 1.0
   Dockerfile (volume handover), deployment files move to `deploy/` and a
   setting is removed. Under `SECURITY.md` only the latest minor receives
   security fixes, so 1.1.0 ends security support for 1.0.x on release day;
   no external operator runs 1.0.x.
10. **Public packages** (Maintainer, 2026-10-05): right after the first
    release push, once the published images' signatures and the harness
    against the published digests have passed (Release Gate).
11. **`NA_ADMIN_LEGACY_SIGNATURES` is removed in 1.1.0** (Maintainer,
    2026-10-05): no deployment relies on it; both maintainer environments run
    1.0.2 clients. The shared signing vectors keep their version 1 fields as
    material a Network Authority must refuse.
12. **Alpine for the Network Authority image** (Maintainer, 2026-10-05):
    `python:3.14-alpine` (same Python 3.14.8) instead of Debian 13 slim.
    Distroless Python is Debian-based and kept 13 distinct high CVEs;
    Chainguard's free tier offers only a moving `latest` tag and no shell.
