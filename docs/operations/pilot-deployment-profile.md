# Pilot Deployment Profile

The supported shape for running a sovereign in a pilot. It is the v1
deployment profile of the {doc}`../development/security-review-v1`, made
concrete, and CI rehearses it on every change
(`scripts/pilot_rehearsal.py`, `.github/workflows/pilot-readiness.yml`).

A sovereign run this way can produce evidence that the project does not claim
yet: an operator outside the project holding its own keys, infrastructure,
policy and revocation (see `ops/plan-v1.0.0.md`, Workstream 2).

## Shape

| Choice | Profile |
| --- | --- |
| Process | `gunicorn genesis_mesh.na_service.wsgi:app` (the container image's entry point), configured only through environment variables |
| Instances | One instance on SQLite, or two or more on PostgreSQL with `NA_HA_MODE=on` behind a load balancer |
| Network | TLS terminated by the operator's reverse proxy or load balancer; `NA_PROXY_HOPS` set to the number of proxies in front (0 if none) |
| Signing key | `NA_KEY_PROVIDER=azure-keyvault` with the instance's managed identity, or `env` from the platform's secret store; never a key file in HA |
| Operator keys | Generated by the operator on its own machines. One privileged key per person who may change trust; standard keys for automation that only evaluates and records |
| Governed workloads | `BOUNDARY_POLICY_ENFORCEMENT=required`, `EVIDENCE_STORE=on` (off by default); anchors copied on a schedule ({doc}`evidence-anchors`) |
| Root key | Offline, never on the NA host; `NA_DEPLOYMENT=managed` (default `local`) makes the NA refuse to start when it finds the root key, or when `NA_RETENTION_REQUIRE_ARCHIVE` is off ({doc}`key-succession`) |
| Clients | The TypeScript SDK (full governed lifecycle), Go or .NET SDK, or raw HTTP |

## Configuration

```bash
GENESIS_FILE=/config/genesis.signed.json
NA_KEY_ID=pilot-na-2026
NA_KEY_PROVIDER=azure-keyvault          # or env, with NA_PRIVATE_KEY_SEED_FILE from the secret store
AZURE_KEY_VAULT_URL=https://<vault>.vault.azure.net
NA_KEY_SECRET_NAME=na-signing-seed
DATABASE_URL=postgresql://...           # omit for a single SQLite instance (DB_PATH)
NA_HA_MODE=on                           # with PostgreSQL and two or more instances
OPERATOR_PUBLIC_KEYS_JSON='{"alice":"<base64>","ci":"<base64>"}'
OPERATOR_KEY_TIERS_JSON='{"alice":"privileged","ci":"standard"}'
BOUNDARY_POLICY_ENFORCEMENT=required
EVIDENCE_STORE=on
NA_PROXY_HOPS=1
NA_PUBLIC_URL=https://na.example.org
NA_DEPLOYMENT=managed
```

All settings are in {doc}`../reference/configuration`. The database needs
code-point (C) collation; see {doc}`high-availability`.

## What the rehearsal proves

Every change runs this flow between two sovereigns with separate keys,
each a gunicorn NA configured from the environment (one on SQLite, one in HA
mode on PostgreSQL):

1. Each operator generates its own root, NA and operator keys; only public
   material crosses between sovereigns.
2. Sovereign A exports and validates B's trust bundle, takes B's key from B's
   live `/sovereign.json`, and issues a scoped treaty. A standard-tier key is
   refused.
3. B attests a member; A accepts it under the treaty and rejects a role the
   treaty does not grant.
4. B revokes the member; A imports B's signed feed and rejects the member. A
   replayed feed and a feed signed by another key are refused.
5. A's database is backed up, restored into a new instance and verified with
   `na verify-db`; the restored instance still holds the treaty and still
   rejects the revoked member.

The recovery drill (`scripts/recovery_drill.py`) does the same for
PostgreSQL: `pg_dump`, `pg_restore` into a new database after the original
is dropped, and a new instance verifying every record and decision.

## Sizing and corporate networks

- **Rate limits count per client address** (the `/node/*` and executor
  limits per key). On SQLite each Gunicorn worker counts on its own, so with
  the default 4 workers a client can reach about four times each limit. Set
  `RATE_LIMIT_STORE=database` for exact limits; it is the default on
  PostgreSQL and required by `NA_HA_MODE=on`. Each governed action makes one
  `/admin/boundary/evaluate` call and one evidence submission. The admin
  limit defaults to 300 requests per minute (30 before v1.1.0) and the
  evidence limit to 120. Behind a corporate proxy or NAT every client shares
  one address, and therefore one budget. Raise
  `NA_RATE_LIMIT_ADMIN_PER_MINUTE` (and `NA_RATE_LIMIT_EVIDENCE_PER_MINUTE`)
  to the pilot's peak, and keep `NA_PROXY_HOPS` correct so the limits apply to
  real client addresses. Failed admin authentications are limited to 30 a
  minute per address and operator key
  (`NA_RATE_LIMIT_ADMIN_AUTH_FAILURES_PER_MINUTE`, per key since 1.2): behind
  one address, a client failing with its own key throttles only that key, and
  one using a key ID the NA does not know throttles only requests naming no
  active key; 120 failures in a minute from the address throttle every
  client. Fix the failing client rather than raising that limit.
- **TLS-inspecting proxies.** Where outbound TLS is re-signed by a corporate
  proxy (Zscaler and similar), clients must trust the proxy's CA:
  `NODE_EXTRA_CA_CERTS=/path/to/proxy-ca.pem` for the TypeScript SDK. Python
  3.13 and later also reject proxy CAs that do not mark their basic
  constraints critical; use the operating system's trust store through the
  `truststore` package for the CLI and Python clients, or run them from a
  network path without inspection.
- **Memory.** One VM with PostgreSQL, two NA instances of two workers and a
  reverse proxy uses about 750 MB; give it 2 GB, or 1 GB plus swap for tests.

## Operations

| Task | How |
| --- | --- |
| Back up | SQLite: `genesis-mesh managed backup`; PostgreSQL: `pg_dump -Fc` (see {doc}`backup-restore`) |
| Restore | Into a new database or file, then `genesis-mesh na verify-db` before serving |
| Upgrade | {doc}`upgrade`: back up, upgrade, verify; rollback is a restore |
| Readiness | `/readyz` for load balancer probes: writable primary, schema version, the NA key in effect |
| Revocation propagation | Import partners' feeds on a fixed schedule (RFC-007); the stale window is the import interval |
| Audit | Audit packs and `genesis-mesh audit verify` from the root key and the anchors you hold ({doc}`audit-packs`, {doc}`audit-verification`); evidence export `GET /admin/evidence/export`, verifiable offline; `genesis-mesh managed audit-export` for the unsigned audit log (SQLite only) |
| Anchors | Copy anchors on a schedule to storage the operator cannot change (`genesis-mesh evidence anchors fetch --anchor-now`, {doc}`evidence-anchors`) |
| Archives | Archive before retention prunes (`genesis-mesh audit archive`, {doc}`audit-and-retention`) |
| Leaving | {doc}`../operators/exit-and-fork` |

## Roles for the pilot

Fill these in before the pilot starts and keep them with the pilot's runbook.

| Role | Responsibility | Who |
| --- | --- | --- |
| Operator | Holds the keys, decides recognition and revocation, runs the NA | *pilot operator* |
| Incident owner | First response to a security or availability incident; follows {doc}`incident-response` | Maintainer |
| Release owner | Ships a fix release (a patch of the current minor version) and confirms the upgrade path | Maintainer |
| Managing partner (if any) | Assists within {doc}`../operators/managing-partner-boundary` | *optional* |

## Limits

- The NA key can be rotated while keeping the sovereign's identity: the
  offline root key signs a key succession ({doc}`key-succession`). That is
  for planned rotation. A compromised NA key, or a compromised root key,
  still means a new identity ({doc}`incident-response`). Keep the NA key in
  Key Vault and the root key offline.
- Imported revocation feeds have no enforced maximum age (SR-07); schedule
  imports to the pilot's tolerance.
- Mesh routing nodes, the Rust gateway and beta surfaces are outside the
  profile (see {doc}`../reference/public-contract`).
